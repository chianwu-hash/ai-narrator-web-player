# AI說書人｜Gemini TTS 小說有聲書製作 SOP

- 版本：2026-08-04
- 適用範圍：小說、故事、遊記等以原文演播為主的產品線
- 參考實作：《臺灣漫遊錄》EP01〈瓜子（上）〉、EP02〈瓜子（下）〉
- 目前模型：`gemini-2.5-flash-preview-tts`
- 目前預設聲線：Speaker1=`Sulafat`、Speaker2=`Aoede`

本 SOP 記錄目前已實測的可用做法與 Gemini TTS 的能力邊界。Preview 模型、免費配額與實際輸出行為都可能變動；每次更換模型或長期停用後重新啟動產線，都必須先用短稿複驗。

## 1. 產品原則與能力邊界

1. 小說產品採「文學演播」，不是主持人談書、摘要或廣播劇。
2. 保留原著字句，不摘要、不改寫、不增補解說。
3. Gemini TTS 的長文輸出具有隨機性。逐字稿正確，不代表每個詞都會讀對，也不代表重跑相同稿件會得到完全相同的表演。
4. 提示詞與發音表只能降低錯誤，不能保證出版級零錯誤。完整人工試聽是正式產線的必要工序。
5. 不以無限重製追求理論完美。主角姓名、核心地名及影響理解的錯誤必須處理；可理解的一次性輕微錯音可記錄後接受。

## 2. 四層稿件必須分開

每一集至少保留以下四層，不得互相覆蓋：

1. **原文清稿**：作品的權威文本，僅移除不應朗讀的編輯標記。
2. **TTS 渲染稿**：包含 Speaker 標記、停頓標記，以及必要的同音字發音替代。
3. **發音指引**：放在實際朗讀文本之前，明確標示不得朗讀；每個 Request 只帶入本段需要的詞。
4. **音訊與 metadata**：WAV、API 回應摘要、聲音活動檢查、錯誤紀錄及人工驗收結果。

原文、字幕及公開逐字稿永遠使用正字；TTS 渲染稿可以為了正確發音使用同音字，但必須另存對照表，不能回寫原文。

## 3. 原文清稿

### 3.1 必做項目

- 確認真正的章節起訖，不把目錄、編輯後記或章末註釋送入 TTS。
- 移除註解編號，例如 `[2]`、`[3]`，同時避免誤刪正文中的合法數字。
- 原書 `※` 不朗讀；保留為結構標記，供切段及後製插入音樂。
- 使用 UTF-8 儲存，重新串回全文後必須與清理後來源逐字一致。
- 記錄來源段落範圍、清理前後字數、移除項目與 `※` 數量。

### 3.2 不可做項目

- 不為了口語順暢而改寫原句。
- 不把註音或同音字直接寫回原文清稿。
- 不用終端畫面中的中文作為唯一校對依據；以 UTF-8 檔案、結構化解析及 diff 驗證。

## 4. 分集、切段與雙聲接力

### 4.1 分集

- 優先在章節、場景轉折或原書 `※` 分集。
- 單集目前以約 15～22 分鐘為舒適範圍；內容完整性優先於硬切固定分鐘數。
- 若一章過長，可拆成上、下集，但章名需明確讀出「上集／下集」。

### 4.2 API Request 切段

- 目前穩定目標：每段約 500～1,400 個清理後原文字元，預估約 2～5 分鐘。
- 建議軟上限：2,200 字；絕對硬上限：2,400 字。
- 音訊 token 盡量低於 12,000；不可接近 16,384 的輸出上限。
- 不從句中切開，優先使用自然段、對話結束或場景轉折。
- 原書 `※` 優先設為 Request 邊界，以便離線插入精確長度的音樂。

過長輸入可能在約 655 秒附近靜默截斷，而且 API 仍可能回傳 `STOP`。因此 `finishReason=STOP` 不是完整性保證。

### 4.3 Speaker 規則

- Speaker1：Sulafat。
- Speaker2：Aoede。
- 第一人稱主角對話原則上由 Speaker1 演播；其他人物對話由 Speaker2 演播。
- 旁白由兩個聲線自然接力，避免單一聲線長時間連續輸出後逐漸產生氣音、機械聲或聲線漂移。
- 單一旁白 turn 以約 135 字為上限；章名標記可視為例外，但正文仍應遵守。
- 相鄰的短旁白段落可以在同一 turn 內合併，以維持自然敘事流動；不要把每個印刷段落機械式拆成獨立 turn。
- 使用 ASCII 別名 `Speaker1`／`Speaker2`，別名與正文放在同一行。

參考格式：

```text
Speaker1: 一。[short pause] 瓜子，下集。…… [short pause] 正文開始。

Speaker2: 下一段原文。
```

## 5. 提示詞與演播方向

正式產線使用 `fiction-audiobook-production` 模式，核心要求如下：

- 兩位都是臺灣女性，成熟、自然、清楚、溫暖。
- 使用臺灣華語，不使用北京腔、兒化音或中國大陸播音腔。
- 文學演播而非主持人對談；兩人延續同一場景與情緒。
- 整體比日常談話稍慢約 5%，但這只能作為方向，不能保證精確語速。
- 情緒從原文自然生長，避免舞臺腔、卡通腔、哭腔與新聞播報腔。
- 逐字朗讀，不得摘要、改寫、增字、刪字或念出 Speaker 標記。

### 5.1 停頓標記

- Developer API 路線目前只採用實測成功的 `[short pause]`。
- 章次後：1 個 `[short pause]`。
- 章名後：省略號加 1 個 `[short pause]`。
- 不在長稿中密集插入 `[medium pause]` 或 `[long pause]`；實測曾出現只生成前段、後半長時間靜音。
- 原書 `※` 的正式產品不依賴提示詞停頓，改由後製插入音樂。
- 非 `※` 的跨 Request 接力，母帶後製插入精確 0.5 秒安靜。

### 5.2 段落呼吸

「印刷段落」不等於「有聲書必須停頓的位置」。正式產線遵守：

- 預設保留相鄰旁白段落的自然合併與連續演播。
- 不在每個原文段落後加入 `[short pause]`。
- 不為每個原文段落建立重複的同聲 Speaker turn。
- 只有語意、思緒、時間或場景明顯轉折，才標記為「呼吸候選點」。
- 呼吸候選點優先在生成後離線插入 0.35～0.5 秒精確安靜，不讓 Gemini 重新決定整段語速與表演。
- 若原始音訊在候選點已經有足夠自然停頓，不再重複插入。
- 插入前以文字—音訊對齊或低能量位置找切點，並做短 edge fade，避免切斷尾音、呼吸或產生爆音。

2026-08-04 A/B 實測使用相同 225 字原文、Sulafat／Aoede 與相同提示：

- A 版將五個段落合併為兩個 turn，時長 56.331 秒。
- B 版保留五個 turn，並在三個同聲段落邊界加入 `[short pause]`，時長 64.251 秒，增加 14.06%。
- 人工試聽確認 A 版節奏較佳。B 版不只增加停頓，也改變整體語速與表演，屬於過度修正。

因此，「語音太滿」不得以每段 pause tag 解決；應保留 A 版的敘事節奏，只對少數真正需要消化的轉折做精確後製。

## 6. 發音處理

### 6.1 一般專名發音表

- 日本漢字人名、地名及已知高風險詞，可以附臺灣華語注音表。
- 注音表放在朗讀文本之前，明確指示不得朗讀。
- 每段只帶入實際出現的詞，避免提示過長。
- 發音表是提示，不是強制 phoneme 控制；正式長文仍可能偶發錯讀。

### 6.2 高影響詞的同音字渲染

主角姓名、核心地名等高頻且影響理解的詞，若發音表仍不穩定，使用 TTS 專用同音字：

| 原文正字 | TTS 渲染字 | 目標讀音 |
|---|---|---|
| 千鶴子 | 千賀子 | ㄑㄧㄢ ㄏㄜˋ ㄗˇ |
| 青山千鶴子 | 青山千賀子 | ㄑㄧㄥ ㄕㄢ ㄑㄧㄢ ㄏㄜˋ ㄗˇ |

2026-08-04 已用 Aoede 朗讀「千賀子老師」、Sulafat 朗讀「青山千賀子」，人工確認可用。測試沒有附發音表，證明同音字渲染本身可以避開錯誤讀法。

使用同音字時必須遵守：

1. 原文清稿、字幕、公開逐字稿不變。
2. 另存正字與渲染字 mapping。
3. 替代字必須具有相同聲母、韻母與聲調。
4. 先用兩個正式聲線及原書語境做短測。
5. 人工確認沒有怪異斷詞後，才套用至正式 Request。

### 6.3 無法預測的錯讀

EP02 人工試聽發現「杏仁」、「燠熱」讀錯，「味噌湯」被帶成日語讀法。這類錯誤可能來自生僻字、多音字、日語語境或模型隨機性，無法在製作前完整列舉。

- 主角姓名等重複高影響詞：必須修正。
- 影響語意或嚴重出戲：只重製受影響的 Request。
- 可理解的一次性輕微錯音：記錄後由人工決定是否接受。
- 不優先採用單句補錄硬接，因為聲線、語氣與接縫可能比原錯音更出戲。

## 7. 生成操作

參考工具：`work/quality_review/gemini_tts_relay_probe.py`

在 `work/quality_review` 執行：

```powershell
python gemini_tts_relay_probe.py `
  book_work_dir\request01.txt `
  book_work_dir\request01.wav `
  --voice-a Sulafat `
  --voice-b Aoede `
  --speaker-a Speaker1 `
  --speaker-b Speaker2 `
  --model gemini-2.5-flash-preview-tts `
  --prompt-mode fiction-audiobook-production `
  --pronunciation-guide book_work_dir\request01_pronunciation.txt `
  --timeout 420
```

若該段不需要發音表，省略 `--pronunciation-guide`。

### 7.1 每次送出前

1. 確認 `GEMINI_API_KEY` 已設定，但不得把 Key 寫入檔案或 log。
2. 檢查同名 WAV 與 metadata 是否已存在且有效；有效成品禁止重複生成。
3. 確認 script、發音表、聲線、模型與輸出檔名。
4. 保存目前 manifest 的「下一個 Request」。

### 7.2 回應處理

- 成功：立即保存 WAV 與 JSON，執行技術 QA，再更新 results 與 manifest。
- `OTHER` 且沒有音訊：保存錯誤；同一段最多重試一次。
- HTTP 429 或其他配額錯誤：立即停止，不重試，保存中斷點。
- 本機命令逾時：不能直接判定 API 失敗。先檢查背景程序、WAV、metadata 與 error JSON；只有確認沒有結果且程序已停止後，才評估是否重送。
- 不啟用 Google Billing、不切換付費專案，也不以多帳號／多專案規避免費限制。

目前免費層實測為每個專案、每個模型每日 10 次請求；這是觀測值，不是永久保證。正式排程應預留失敗與重試額度。

## 8. 每段技術 QA

每個 Request 至少檢查：

- WAV：單聲道、24 kHz、16-bit PCM。
- API 有音訊 part，`finishReason=STOP`。
- 聲音活動檢查通過；不得有 10 秒以上持續低訊號。
- 音訊 token 低於 12,000；若偏高，下一輪縮短段落。
- 長段必須驗證結尾句存在；必要時用 ASR 或自然尾端 sentinel 檢查完整性。
- metadata 的 script、聲線、模型、字數、時長與輸出檔相符。

技術 QA 只能發現格式、持續靜音與明顯截斷，不能判斷機械聲、口音、人物感、情緒或正確發音。

## 9. 人工試聽 QA

必須用正常播放速度完整聽完母帶，至少檢查：

1. 章次與章名停頓。
2. 每個 Request 的前段、中段與後段是否出現氣音、雜音、機械聲或聲線漂移。
3. 兩個聲線切換是否自然，是否出戲。
4. 主角姓名、人物名、地名、生僻字及日語借詞。
5. 情緒是否克制、連續，沒有突然變成播報腔或舞臺腔。
6. `※` 音樂是否提供足夠消化時間。
7. 跨 Request 接點是否有爆音、突切或不自然空白。

### 9.1 錯誤處置分級

| 等級 | 範例 | 處置 |
|---|---|---|
| A：必修 | 主角姓名錯讀、內容遺漏、長靜音、嚴重機械聲 | 修改渲染稿或縮段，只重製受影響 Request |
| B：評估 | 影響理解的詞、明顯異常口音、持續數句的表演失控 | 比較重製風險後決定 |
| C：可接受 | 一次性輕微錯音、仍可理解且不影響情節 | 記錄，不必為零錯誤反覆抽卡 |

重製是重新抽樣，可能修好一處又產生新錯誤；重製後必須重新完整試聽該 Request。

## 10. `※` 音樂過門與母帶

### 10.1 2026-08-04 起的新基準

- 一般 `※`：12 秒音樂。
- 明顯情節或場景轉換：15 秒音樂。
- 章節／集數結束：18～20 秒音樂。
- 一般 `※` 的建議節奏：前置安靜 0.5 秒＋音樂 12 秒＋後置安靜 0.8 秒，總喘息約 13.3 秒。
- 不把既有八秒音樂直接降速拉成十二秒；應由完整原曲重新剪成完整樂句，或在音樂結構允許的位置延長後淡出。

現有 02、03、04 號檔案是八秒歷史版本。EP01、EP02 保留當時成品，不回溯重做；後續正式集數必須先完成十二秒版音樂素材。

### 10.2 音樂規格

- 目前音量目標：約 −26 LUFS，峰值約 −5 dBTP。
- 單聲道、24 kHz、16-bit PCM WAV。
- 保留自然淡入、淡出，不從不完整樂句中硬切。
- 02、03、04 號可依場景情緒輪替；使用順序寫入母帶 metadata。

### 10.3 母帶拼接

- 非 `※` 的 Request 接點：0.5 秒安靜。
- `※` 接點：依本節插入前置安靜、音樂、後置安靜。
- 段落呼吸候選點：確認原始停頓不足後，離線補足 0.35～0.5 秒；不得對每個印刷段落批次插入。
- 每個語音及音樂組件首尾使用約 8 ms edge fade，避免爆音。
- 驗證每個拼接邊界回到零振幅。
- 組合完成後再次執行 WAV 格式、總時長、聲音活動與 SHA-256 檢查。
- 未經產品決策，不自行增加片頭或片尾音樂。

## 11. 紀錄與交付

每集工作目錄至少保存：

- 原文清稿。
- 每個 Request 的 TTS 渲染稿。
- 每段發音表。
- 正字／同音渲染 mapping。
- 每段 WAV、metadata、stdout／stderr 與錯誤 JSON。
- `manifest.json`：來源、切段、聲線、接點與目前狀態。
- `results.json`：生成結果、時長、token、QA 與母帶摘要。
- `README.md`：人可以快速閱讀的製作與人工驗收紀錄。
- 完整母帶 WAV 與母帶 metadata。

交付時附上完整母帶試聽檔、總長、音樂時間點，以及仍待人工驗收的風險。
